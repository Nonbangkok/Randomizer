Client-Side Processing: The Future of Web Privacy

The dominant model of the web for 30 years has been client-server: you send your data to a server, it processes it, sends back results. For most applications this model works well enough — but for anything privacy-sensitive, it is fundamentally broken. When your data leaves your device, you lose control of it. A better paradigm exists, and it is already running in your browser today.

The Server-Trust Problem

Every time you use a server-side tool, you are implicitly making four assumptions. First, that the server does not log your inputs. Second, that the operator's privacy policy is truthful and will remain so. Third, that the server is secure against breaches. And fourth, that no undisclosed third parties have access to your data.

In practice, all four assumptions fail with alarming regularity. Consider what happened to LastPass in 2022: encrypted password vaults were exfiltrated from their servers. The data was "encrypted," but the encryption keys were tied to master passwords — passwords that attackers then had unlimited time to crack offline. The breach was possible only because the data existed on a server in the first place. If password generation and storage had happened entirely client-side, there would have been nothing to steal.

The pattern repeats across the industry. Analytics platforms harvest behavioral data from the tools you use to analyse your own data. "Free" services — search tools, grammar checkers, productivity apps — frequently have business models built around selling or processing user inputs. A grammar checking tool that processes your private documents on its servers knows everything you type. A resume tool that generates suggestions server-side has read every resume you upload. The privacy policy may promise not to misuse it, but the architectural reality is that the data is there, on their infrastructure, under their control.

The fundamental problem is not bad actors (though those exist too). It is that the server-side model makes privacy a policy question when it should be an engineering guarantee. When data never reaches a server, no policy, no breach, and no subpoena can expose it. The only way to guarantee privacy is to eliminate the server from the computation entirely.

WebAssembly: Running Native Code in Your Browser

For most of the web's history, "runs in your browser" meant JavaScript — a language fine for UI interactions but poorly suited to computationally expensive tasks like cryptographic key generation or complex probabilistic simulations. If you needed serious processing power, you needed a server. That constraint no longer holds.

WebAssembly (WASM) is a binary instruction format that executes directly in the browser's sandboxed runtime. Standardised by the W3C in 2017 and supported by every major browser since 2018, it enables code written in systems languages like Rust, C, and C++ to run inside a web page at near-native speeds. Performance benchmarks consistently show WASM executing at 80–90% of equivalent native code, with further gains ongoing as browser engines optimise their WASM runtimes.

The privacy implication is significant. Operations that were previously too expensive to run in a browser — AES encryption, argon2 password hashing, complex random generation algorithms — can now execute client-side in milliseconds. The computational barrier that once forced developers to delegate sensitive work to servers has largely dissolved.

This is not a niche technology. Figma, the collaborative design tool used by millions of professional designers, runs its entire rendering engine in WASM. AutoCAD Web brings CAD software to the browser without a server-side rendering backend. Google Earth Web handles complex 3D globe rendering client-side. These are serious, performance-intensive applications — not toy demos. If a 3D design tool can run natively in your browser, so can a password generator.

The security model matters too. WASM executes inside the browser's existing sandbox: it cannot access the filesystem, cannot make arbitrary network requests, and cannot escape the tab it runs in. The same constraints that protect you from malicious websites protect your data when you run a privacy-sensitive tool built on WASM.

What "Runs in Your Browser" Actually Means

When a website claims a tool "runs entirely in your browser," it is a specific technical claim — but many users aren't sure what it means or how to verify it. Let's demystify it.

When you visit a website, your browser downloads a collection of files: HTML, CSS, JavaScript (or WASM), and assets. These files are transferred to your machine over HTTPS, cached locally, and then executed. For a client-side tool, that initial download is the only network activity. Everything that happens after — all the computation, all the generation, all the processing — happens on your CPU, reads and writes only to your local memory, and produces results that only you see. No further requests leave your device.

You can verify this yourself using browser developer tools. Open any page, navigate to the Network tab in DevTools (F12 in most browsers), and clear the log. Then use the tool: generate a password, produce a random result, process some text. Watch the network log. For a properly implemented client-side tool, you will see zero new requests during operation. The network log stays empty. There is nothing to intercept, nothing to log server-side, nothing to breach.

Contrast this with a server-side tool. Every interaction — every keystroke in some cases, certainly every "generate" button press — triggers a network request. That request contains your input data. It travels to a server, where it is processed, and where it may be logged, analysed, or stored. You can see these requests in the same Network tab: a POST request fires every time you interact with the tool, carrying your data as its payload.

The verification step is important because "client-side" is a marketing claim as much as a technical one. Not every tool that claims to run locally actually does. DevTools gives you ground truth.

The Limits and Trade-offs

Client-side processing is not a universal solution, and intellectual honesty requires acknowledging where it falls short.

The most significant caveat is that the code itself is downloaded from a server. If that code is tampered with — either at the source or via a man-in-the-middle attack — you could be running malicious logic. This is why two factors are non-negotiable for trustworthy client-side tools: open-source code (so anyone can audit what the tool actually does) and HTTPS (so the code cannot be tampered with in transit). A closed-source client-side tool still requires trusting the operator's good intentions; the advantage over server-side is only that the attack surface is reduced, not eliminated.

Large machine learning models present a practical barrier. A modern LLM might weigh tens of gigabytes — impractical to ship to every user's browser. For AI-powered tools, some server involvement remains necessary for now, though this boundary is moving as model compression improves and edge inference hardware matures.

Collaboration and synchronisation inherently require a server. If two users need to share state — a multiplayer game, a shared document, a collaborative playlist — that data must live somewhere both can reach. Client-side architecture cannot solve the synchronisation problem.

And client-side code must be re-downloaded when it is updated. For applications that need frequent updates, this adds latency compared to a server that updates instantly for all users.

But for the category of tools this matters most for — privacy-sensitive, single-user utilities like password generation, personal data processing, and random generation — these trade-offs are largely irrelevant. The computation is lightweight enough to run in the browser. There is no collaboration requirement. Open-source code is achievable. HTTPS is standard. For this category, client-side is not just preferable: it is strictly superior. As WASM matures and devices become more powerful, the category of tools that can viably move client-side will only grow.
